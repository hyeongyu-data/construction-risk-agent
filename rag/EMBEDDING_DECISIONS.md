면접에서 "왜 이걸 썼어요?"에 답하기 위한 각 기술 결정의 트레이드오프 정리.

## 1. PostgreSQL(pgvector) vs Pinecone

**선택: pgvector**

이미 RDS에 비용/날씨/자재 데이터가 집중되어 있어서, 벡터도 같은 DB에 두면 인프라 추가 없이 관계형 데이터와 JOIN이 가능하다.

```sql
-- 예: 철근 계약단가 + 프로젝트 정보 한 번에 조회
SELECT c.content, p.project_name, p.region
FROM rag.company_docs c
JOIN projects p ON c.project_id = p.id
ORDER BY c.embedding <=> $1
```

Pinecone은 벡터 전용이라 이런 JOIN이 불가능하고, 별도 인프라 비용과 관리 포인트가 생긴다.

**Pinecone이 더 나은 케이스:**
- 벡터 수백만 개 이상 대규모
- 밀리초 단위 응답이 필요한 서비스
- 인프라 관리를 완전히 위임하고 싶을 때

**우리 상황:** 건설 프로젝트 문서 수백 개 수준이므로 pgvector 성능으로 충분하고, 운영 복잡도가 낮다.

## 2. Bedrock(Titan Embed v2) vs OpenAI vs 오픈소스 모델

**선택: amazon.titan-embed-text-v2:0**

**이유 1 — 데이터 보안:**
계약서, 기성청구서, 견적서는 민감한 사내 문서다. OpenAI API를 쓰면 데이터가 외부 서버로 전송된다. Bedrock은 AWS 인프라 안에서 처리되므로 데이터가 외부로 나가지 않는다.

**이유 2 — 인프라 통일:**
RDS도 AWS, API 서버도 AWS. 네트워크 지연과 비용이 최소화되고, IAM으로 접근제어를 통합 관리할 수 있다.

**이유 3 — 운영 복잡도:**
오픈소스 모델(klue/roberta 등)은 GPU 서버를 직접 운영해야 한다.

**알고 있는 단점:**
Titan은 한국어 특화 모델이 아니다. `klue/roberta-base` 같은 한국어 특화 모델이 건설 도메인 한국어 검색에서 더 높은 정확도를 낼 수 있다. 다만 self-hosted 운영 복잡도 대비 정확도 향상폭이 현재 단계에서 정당화되지 않는다고 판단했다. 서비스 규모가 커지면 재검토할 지점이다.

## 3. pdfplumber vs PyPDF2 vs pymupdf

**선택: pdfplumber**

표준품셈 PDF는 텍스트보다 **테이블 구조**가 핵심이다.

| 라이브러리 | 텍스트 추출 | 테이블 구조 보존 | 속도 |
|-----------|------------|----------------|------|
| PyPDF2    | ✅          | ❌ (셀 구분 사라짐) | 빠름 |
| pymupdf   | ✅          | △ (좌표 기반)   | 매우 빠름 |
| pdfplumber | ✅         | ✅ (셀 단위 추출) | 보통 |

품셈 테이블 한 행 예시:
```
콘크리트공 | 인 | 0.2 | 0.18 | 0.15
```
PyPDF2로 추출하면 `콘크리트공인0.20.180.15` 처럼 뭉개진다. pdfplumber의 `extract_tables()`는 셀 단위로 분리해서 의미 있는 구조를 유지한다.

## 4. 청킹 전략

### 4-1. company_docs — 500자 슬라이딩 윈도우

```python
CHUNK_SIZE    = 500
CHUNK_OVERLAP = 80
```

**왜 500자?**
계약서 조항 하나(`제1조 계약금액...`)가 평균 300~600자 내외다. 500자로 잡으면 하나의 조항이 대부분 한 청크 안에 들어온다.

**왜 overlap 80자?**
조항 경계에서 청킹이 잘릴 때, 다음 청크가 앞 문맥 80자를 포함해서 "이 조항이 무엇에 대한 건지" 문맥이 유지된다.

**1차 분리 기준:**
```python
sections = re.split(r'(?=제\d+조)', text)
```
먼저 조 단위로 나누고, 조 내부가 길면 슬라이딩 윈도우로 추가 분리한다.

**알고 있는 한계:**
고정 사이즈 청킹은 테이블 중간을 자를 수 있다. Semantic chunking(문장 임베딩 유사도 기반 경계 탐지)이 더 정확하지만 구현 복잡도와 처리 비용이 높다.

### 4-2. labor_cost — 섹션코드 기준 청킹

```python
raw = re.split(r'(?m)^(?=\d+-\d+-\d+)', full_text)
```

**왜 섹션코드(`5-3-1`) 기준?**
표준품셈은 `5-3-1 철근 배근` 같은 섹션코드가 **의미 단위**다. 이 경계를 무시하고 고정 사이즈로 자르면 "5-3-1이 뭔 항목인지" 문맥이 잘린 청크가 생긴다.

품셈 수치(인/단위)와 공종명이 같은 섹션 안에 있어야 검색 결과가 실제로 유용하다.

**일당 → 단위당 환산 주석 삽입:**
```
[※ 일당→㎥당 환산]
  콘크리트공: 0.2인/일 ÷ 5㎥/일 = 0.04인/㎥
```
PDF에 "(일당)" 기준으로 기재된 항목을 단위당으로 자동 환산해서 청크에 추가한다. 에이전트가 직접 계산 없이 인/㎥ 단위로 바로 쓸 수 있게 하기 위해서다.

## 5. 검색 방식 — 순수 벡터 검색

**현재:** `embedding <=> query_embedding` (코사인 유사도)

**알고 있는 한계:**
"H형강 200×200" 같은 규격명, "SD400" 같은 코드는 의미보다 **정확한 키워드 매칭**이 중요하다. 벡터 검색만으로는 이런 케이스에서 검색 누락이 생길 수 있다.

**개선 방향 — 하이브리드 검색:**
```
최종 점수 = α × 벡터유사도 + (1-α) × BM25점수
```
pgvector + `pg_trgm` 또는 PostgreSQL 전문검색(`tsvector`)을 결합하면 키워드 정밀도와 의미 검색을 동시에 잡을 수 있다. 현재는 단계적 구현을 위해 벡터 검색 먼저 검증 중이다.

## 6. 트러블슈팅 — 실제 발생한 검색 품질 문제

### 6-1. `get_labor_price` LIKE 검색 오매칭

**현상:**
"철골공"으로 검색하면 `WHERE job_type LIKE '%철골공%'`이 "경량철골공"도 잡는다. `ORDER BY year DESC LIMIT 1`만 걸려 있어서 어떤 직종이 반환될지 보장이 없었다.

**원인:**
LIKE 부분 일치는 포함 관계를 구분하지 못한다. "철골공"을 찾고 싶어도 이름이 더 긴 직종이 먼저 걸릴 수 있다.

**해결:**
정확 일치(`=`) 먼저 시도하고, 없을 때만 LIKE 검색으로 폴백. LIKE 결과는 `LENGTH(job_type) ASC`로 이름이 짧은 것(가장 구체적인 매칭)을 우선 반환.

```python
# 1순위: 정확 일치
WHERE job_type = %s ORDER BY year DESC LIMIT 1

# 2순위: LIKE 검색 + 이름 길이 짧은 순
WHERE job_type LIKE %s ORDER BY year DESC, LENGTH(job_type) ASC LIMIT 1
```

**교훈:**
부분 일치 검색은 "포함 여부"만 확인하므로 더 긴 직종명에 의해 의도치 않게 오매칭된다. 도메인 특화 검색에서는 정확 일치를 1순위로 두는 게 안전하다.

---

### 6-2. 벡터 검색 — 낮은 유사도 청크 혼입

**현상:**
"철골 세우기" 쿼리로 `search_standard_spec` 호출 시 `1-2-1 현장 세우기`(정답) 외에 `1-4-4 경량형강철골조`, `6-7-9 모듈러 건축 설치`까지 함께 반환됐다. 에이전트가 스스로 골랐지만, 유사도 낮은 청크가 컨텍스트를 오염시킬 수 있다.

**원인:**
`LIMIT 5`로 무조건 5개를 반환하고 유사도 점수를 걸러내는 로직이 없었다. pgvector 코사인 거리는 0~2 범위인데, 거리가 멀어도 상위 N개가 그냥 반환된다.

**해결:**
코사인 거리 임계값(`SIMILARITY_THRESHOLD = 0.45`)을 도입해 임계값 이하 청크만 채택. 전부 초과하면 최상위 1개를 경고 메시지와 함께 반환해 에이전트가 낮은 품질임을 인지할 수 있게 했다.

```python
SELECT content, embedding <=> %s::vector AS distance
FROM rag.standard_spec
ORDER BY distance
LIMIT 5
-- 이후 Python에서 distance <= 0.45 필터링
```

**임계값 튜닝 기준:**
- 0.45 이하: 같은 챕터 내 유사 공종
- 0.45~0.6: 관련 있지만 다른 공종
- 0.6 이상: 무관한 섹션

실제 운영 중 로그를 보면서 조정 필요. 너무 낮으면 "결과 없음"이 자주 발생하고, 너무 높으면 지금이랑 차이 없다.

**교훈:**
벡터 검색은 "가장 유사한 N개"를 반환하지만 그 유사도가 충분히 높은지는 별도로 검증해야 한다. 임계값 없는 Top-K는 저품질 결과를 보장 없이 포함시킨다.

## 요약 트레이드오프 테이블

| 결정 | 선택 | 포기한 것 | 선택한 이유 |
|------|------|-----------|------------|
| 벡터 DB | pgvector | Pinecone의 확장성 | 관계형 데이터 JOIN, 인프라 통일 |
| 임베딩 모델 | Bedrock Titan | 한국어 특화 정확도 | 데이터 보안, AWS 통합, 운영 단순화 |
| PDF 라이브러리 | pdfplumber | 처리 속도 | 테이블 구조 보존 |
| 청킹 (계약서) | 500자 슬라이딩 | Semantic chunking 정확도 | 구현 단순성, 조항 단위와 맞음 |
| 청킹 (품셈) | 섹션코드 기준 | 균일한 청크 크기 | 의미 단위 보존 |
| 검색 | 벡터 검색 | 키워드 정밀도 | 단계적 구현, 향후 하이브리드로 확장 예정 |
